# V1.2.0 首屏性能排查

排查日期：2026-11-16；实现日期：2026-11-17。基线 `f8ae0ae`，生产构建，Chrome for Testing 151.0.7922.34，1440×900，独立临时 profile 中的 200 个测试书签。下方原始排查记录描述隔离实验；正式实现和本次验证见末尾。GitHub V1.2.0 Release 未替换。

## 结论

有优化空间，主要在后台休眠后的启动链和屏幕外 favicon 加载。原来的 170ms 是一次测试进程侧测量，不能据此断言页面稳定耗时 170ms，也不能据此证明 200 张卡片渲染超过 100ms。

后台已运行时，新建测试页的 DOM 就绪中位数为 62ms，DOM 就绪后经过两次 requestAnimationFrame 的时间为 92ms。后台停止后，对应值约为 116–119ms 和 146–148ms。隔离实验组合使后一场景分别降到约 110–112ms 和 128–130ms，仍未达到所有场景稳定低于 100ms。

## 测量口径

旧的 `tests/real-chrome-check.mjs` A12 从 Node.js 的 Date.now() 开始计时，调用 page.reload()，再等待 waitForFunction() 发现至少一张卡片。它包含浏览器控制通信、导航和轮询等待，既没有等待全部 200 项，也没有断言 100ms 阈值；测试名称中的小于 100ms 不能作为达标依据。

新增 `tests/performance-check.mjs` 用页面内计时和观察器记录：

- ready：全部 200 张卡片出现在 DOM 中、加载骨架消失、首张书签存在 href。它是 DOM 就绪代理，不是标准 TTI，也没有测量真实输入响应。
- frameReady：DOM 就绪后经过两次 rAF。用于观察帧调度等待，不能视为精确的像素呈现时刻。
- wallMs：测试进程发起导航到观察到帧标记，包含自动化控制开销。
- API 起止：设置读取、tree 和 children 消息请求耗时。

分别测量刷新、新建页、每次停止 service worker 后新建页。下表使用每批剔除第一次导航后的中位数。每批首次导航单独保留在 JSON 中，避免把 profile 首次页面初始化混入后续重复测量；首次 DOM 就绪通常约 180–250ms，样本不足以推断其稳定分位数。

## 实测

| 场景与版本 | 后续样本数 | DOM 就绪中位数 | 两次 rAF 标记中位数 | 测试进程耗时中位数 |
|---|---:|---:|---:|---:|
| 基线，刷新 | 11 | 74.4ms | 87.5ms | 89.8ms |
| 基线，新建页，后台已运行 | 11 | 62.0ms | 92.2ms | 98.5ms |
| 基线，新建页，后台停止 | 7 | 116.1ms | 146.3ms | 151.8ms |
| 组合实验，新建页，后台停止 | 7 | 110.1ms | 128.4ms | 133.4ms |
| 基线复测，新建页，后台停止 | 11 | 118.6ms | 148.0ms | 154.4ms |
| 组合实验复测，新建页，后台停止 | 11 | 111.8ms | 130.3ms | 136.4ms |

组合实验包括：轻量入口提前并行发起存储与树请求、使用树中已有的 children、面板异步加载、书签快照 shallowRef、favicon 原生懒加载。复测中两帧标记和测试进程耗时均改善约 18ms（约 12%），DOM 就绪改善约 7ms。实验是分批顺序运行的，仍有负载和帧调度差异，不能把组合差值归因给单个修改。

## 发现与优化点

### 1. 启动串行，后台唤醒较晚

`src/entrypoints/newtab/main.ts` 先加载 Vue、App 和校验依赖，读取设置、应用主题并挂载 App；App 在 onMounted 中再请求书签树。service worker 停止后，树请求约 19–44ms，后台已运行时通常约 3–6ms；部分停止后台的样本中存储读取也有约 23–26ms 等待。

建议提前发起树读取，与设置读取和 UI 模块加载重叠；继续在主题确定后挂载，以保留启动无主题闪烁的行为。完整树仍应来自 Chrome API，不应把书签数据库缓存到 storage。

### 2. 200 个 favicon 都立即加载

`src/components/BookmarkCard.vue` 没有图标懒加载策略。200 张卡片共约 1,654 个 DOM 元素，屏幕外图标也立即发起读取。

实验加 loading=lazy 后，采样点完成的图标约为 92 个，而非 200 个；浏览器会预加载靠近视口的图标，并非只加载可见项。DOM 总数不变，仍使用 Chrome 本地 favicon 服务。此项减少首屏图标工作，主要改善帧等待，不能保证 DOM 就绪等比例改善。

建议优先验证快速滚动、列表视图、图标失败降级和键盘操作后落地。

### 3. 未打开面板进入首屏脚本

首页脚本约 210.8KB，编辑、删除、移动、设置、搜索、维护、最近使用和标签面板均静态导入。实验异步加载这些面板后，UI 主块约 194–196KB，启动器约 2.4KB；总包略增，收益在首屏推迟工作，不在 ZIP 大小。

懒加载与并行读取组合使刷新 DOM 中位数从 74.4ms 到 68.3ms，但帧标记几乎不变（87.5ms 到 87.6ms），不能单独保证明显加速。正式采用时需验证面板首次打开的焦点和错误状态。

### 4. 树之后重复读取子项

`src/App.vue` 的 refresh() 在 tree 之后再串行请求 children，而 target.children 已有当前目录子项。第二次请求通常约 1.4–2.4ms。

仅取消它，刷新 DOM 中位数从 74.4ms 到 72.9ms，帧标记没有改善。可作为简化和小幅优化，但不是主要瓶颈。同一快照还能避免两次 API 返回不同时间点的数据；仍需验证外部移动/删除、事件刷新和空目录。

### 5. 校验依赖与后台脚本体积

后台产物约 95.7KB。Rollup 依赖图显示 Zod 是后台的主要依赖之一，首页也包含 Zod 和 Vue。分析器模块长度在压缩前统计，不能直接当作最终字节占比。

简单将后台处理器改为动态 import 没有分块，仍输出约 97.4KB 的单文件，性能没有改善，故不推荐该实验方案。若以后精简校验依赖，需要保留消息校验、URL 限制和错误提示，并单独验证收益。

### 6. 暂不推荐虚拟列表或 shallowRef 改造

数据响应结束到 DOM 就绪通常约 9–17ms。200 项场景尚未显示出必须用虚拟列表解决的成本；shallowRef 实验也没有超出噪声的改善。虚拟列表还会增加拖拽、键盘和定位复杂度，当前优先级低。

## 建议顺序

1. 固定性能口径，分别报告首次初始化、后台已运行和后台停止场景，注明 100ms 目标对应的指标。
2. 优先验证 favicon 懒加载和启动读取并行，保留主题初始化、原生书签唯一数据源和错误处理。
3. 顺带取消冗余 children 请求；面板异步加载作为后续启动体积优化。
4. 完整回归后再替换本地包。排查当天未更新正式应用；次日实现见下方。

## 复现与原始资料

```sh
pnpm build
node tests/performance-check.mjs
OWNTAB_PERF_MODE=new-tab node tests/performance-check.mjs
OWNTAB_PERF_MODE=cold-worker OWNTAB_PERF_SAMPLES=12 node tests/performance-check.mjs
```

默认报告写入 artifacts/performance/baseline.json，可用 OWNTAB_PERF_OUTPUT 指定路径、OWNTAB_EXT 指定实验构建。测试不使用日常书签，临时 profile 结束后删除。

本次原始 JSON 与 bundle-stats.html 在被 Git 忽略的 artifacts/performance/；实验源码在 .tmp-debug/performance-experiment/，组合代码差异另存 combined-prototype.patch。

限制：使用 200 个 example.com 书签、空标签和置顶数据、固定桌面尺寸、扩展页面直达 URL；CDP 停止 worker 不模拟完整 OS 冷缓存或浏览器启动。图片懒加载受 Chrome 预加载距离影响。实验样本有限且未做全部功能回归，不能把结果视为正式应用已优化或稳定达到 100ms。

## 2026-11-17 正式实现与验证

已将下列改动落入应用代码：

- main 通过无 Vue/Zod 依赖的 startup 模块并行发起存储和树请求，再动态加载 bootstrap。主题校验、应用仍在挂载前完成，存储仍只读取一次。
- 预取期间监听书签变更和导入状态；注册 App 的实时监听后再移除早期监听。过期快照会重新读取，挂载后到达的旧请求由代际标记丢弃。预取仅消费一次，失败重试读取新快照。
- 当前目录直接使用完整树中的 children，减少一次消息/API 往返，并使用同一时间点的数据。
- 书签及置顶图标使用原生懒加载；编辑、删除、移动、设置、搜索、维护、最近使用、标签面板在打开时加载。
- 不采用未显示稳定收益的 shallowRef 或后台动态导入方案，不引入虚拟列表。

当天先重跑原版，再测修改版，均为 12 次导航；剔除每批首次页面初始化后取 11 次中位数。机器负载与前一天不同，采用当天对照，不能将前一天的 170ms 直接与本次页面内指标相减。

| 场景 | 指标 | 修改前 | 修改后 |
|---|---|---:|---:|
| 后台停止 | 全部 200 项 DOM 就绪 | 91.4ms | 80.1ms |
| 后台停止 | 两次 rAF 标记 | 115.3ms | 96.7ms |
| 后台停止 | 测试进程耗时 | 119.5ms | 100.7ms |
| 后台已运行 | 全部 200 项 DOM 就绪 | 49.2ms | 46.5ms |
| 后台已运行 | 两次 rAF 标记 | 72.4ms | 62.6ms |

后台停止场景的两帧中位数改善约 16%；首次初始化仍更慢，后续样本也有超过 100ms 的情况，不能据此承诺所有场景低于 100ms。原始结果为 artifacts/performance/before-20261117-{cold,warm}.json 和 after-20261117-{cold,warm}.json。

最终构建再次测量：后台停止时 DOM 就绪中位数 78.5ms、两帧 95.0ms、测试进程 99.8ms；随后重测原版分别为 83.7ms、106.3ms、113.0ms，说明原版基线也随系统状态变化。该轮两帧改善约 11%，结合前一轮应报告约 10%–16% 的观察改善，而非固定百分比。后台已运行最终测量 DOM 中位数 46.8ms、两帧 63.6ms。两帧的后台停止后续样本最大值仍有 101.5ms，profile 首次初始化的 DOM 为 158.3ms，不宣称全场景小于 100ms。结果文件：final-20261117-{cold,warm}.json、baseline-repeat-20261117-cold.json。

类型检查、164 项单测、20 组浏览器布局与主要交互检查、真实 Chrome 12/12 均通过。新增浏览器覆盖挂载前/后预取失效、导入交接、预取失败重试；真实 Chrome 验证 200 项完整渲染、滚动后图标加载、列表视图焦点。A12 已改名为完整渲染与导航耗时记录，不再以小于 100ms 的名称暗示达标；专用脚本记录页面内指标。

本地 .output/chrome-mv3 和 .output/owntab-1.2.0-chrome.zip 已更新，ZIP 中 21 个文件与构建目录逐文件一致，权限仍仅为 bookmarks/storage/favicon。版本号保留 1.2.0，优化记录置于 CHANGELOG 的 Unreleased；远端 GitHub Release 仍是原始 1.2.0 文件。

从 Git 64dcf39 单独构建已验收的 V1.2 优化版本作为对照。仍用 Chrome for Testing 151、1440×900、200 个 example.com 书签、独立临时 profile；每组 12 次导航，首次单独报告，以下为其余 11 次的中位数。

## V1.4 功能实现后的性能回归（2026-11-20）

Chrome for Testing 153、1440×900、200 个 example.com 书签、空标签/置顶数据，`reload` 模式 12 次。页面 ready 中位数 27.5ms，下一动画帧标记中位数 41.2ms；后续样本的 p95 为 37.7ms 与 51.8ms。包含首次初始化的完整样本 p95 为 239ms 与 259.4ms，反映首个 profile 页面仍有长尾，故不以中位数宣称每次启动均低于 100ms。

真实扩展完整导航检查另测得 87ms（Playwright 测试进程口径）。模拟浏览器的 20 组数量/视口布局检查通过。该组测试没有标签、备注、置顶或自定义引擎的大数据负载，后续若本地数据显著增长应增加相应性能样本。结果文件：`artifacts/performance/baseline.json`。
